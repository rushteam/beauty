# DB Resilience — Circuit Breaking + Bulkhead + Pool Saturation Protection

> 中文版: [db-resilience.md](db-resilience.md)

For failures of the **InnoDB row-lock contention → Error 1205 → connection pool exhaustion → site-wide cascading failure** kind, beauty provides optional degradation protection at the DB access layer.

> **Scope**: this is an anti-cascade **mechanism**, not a business fix. Synchronous writes to hot rows still need to be made asynchronous / batched / throttled.

## ORM Selection (Scaffolding / New Projects)

Projects generated by `beauty new` **ship without an ORM by default**; you wire up the persistence layer yourself from `contrib/`. If **no** ORM is specified when creating the project, the recommended priority is:

| Priority | Module | Use case |
|--------|------|----------|
| **1 (default recommendation)** | [`contrib/bun`](../contrib/bun) | Regular CRUD, relational queries, an ORM with lighter dependencies |
| 2 | [`contrib/gorm`](../contrib/gorm) | Teams with existing GORM experience, ecosystem plugins |
| 3 | [`contrib/sqldb`](../contrib/sqldb) | sqlc / sqlx / hand-written SQL, strongly typed query generation |

```bash
go get github.com/rushteam/beauty/contrib/bun@latest    # preferred when unspecified
go get github.com/rushteam/beauty/contrib/gorm@latest   # optional
go get github.com/rushteam/beauty/contrib/sqldb@latest  # sqlc scenarios
```

> **Bun caveat**: `Update` **skips Go zero values** by default (`0`, `""`, `false`, `nil`, etc.), so you cannot "update a field to its zero value" that way. Use an explicit `Set("col = ?", val)` or `Column("col")` — see [contrib/bun/README.md](../contrib/bun/README.md#update-与零值).

## Module Mapping

| Scenario | Module | Underlying layer |
|------|------|------|
| sqlc / sqlx / hand-written SQL | `contrib/sqldb` | Native `database/sql` |
| GORM | `contrib/gorm` | ORM, still `database/sql` underneath |
| Bun | `contrib/bun` | ORM, still `database/sql` underneath |

The core logic is the `Guard` in `contrib/sqldb`; GORM hooks in via a Plugin and Bun via a QueryHook.

## Three Layers of Protection

1. **Circuit breaking** — 1205 / 1213 / deadline / connection errors above the threshold → `sqldb.ErrCircuitOpen`
2. **Bulkhead** — `MaxConcurrent` limits in-flight SQL (mainly covers Exec / Query)
3. **Pool saturation** — `InUse == MaxOpen` and `WaitCount` growing → `sqldb.ErrPoolSaturated`

**Reads and writes must be wrapped separately**, so that a write hotspot does not trip the breaker on the read path as well.

## sqldb (sqlc / sqlx)

```go
import (
    _ "github.com/go-sql-driver/mysql"
    "github.com/rushteam/beauty/contrib/sqldb"
    appdb "yourapp/db" // generated by sqlc
)

sdb, _ := sqldb.Open(sqldb.Config{
    Driver: "mysql", PrimaryDSN: "...", ReplicaDSNs: []string{"..."},
    MaxOpenConns: 50,
})
defer sdb.Close()

pool := sdb.Primary()

writeQ := appdb.New(sdb.ResilientWriter(sqldb.DefaultWriteResilience(pool)))
readQ  := appdb.New(sdb.ResilientReader(sqldb.DefaultReadResilience(pool)))

// or wrap manually
write := sqldb.WithResilience(sdb.Writer(), sqldb.PathResilience{
    Breaker:       &sqldb.BreakerSettings{Threshold: 0.3, MinRequests: 5},
    MaxConcurrent: 20,
    Pool:          pool,
})
```

### Custom Failure Classification

```go
sqldb.PathResilience{
    IsFailure: sqldb.DefaultIsFailure, // default: 1205/1213/deadline/connection
    // or custom:
    IsFailure: func(err error) bool {
        return sqldb.DefaultIsFailure(err) || errors.Is(err, myAppErr)
    },
}
```

### QueryRow Limitation

The standard library's `QueryRow` only sends the SQL at `Scan` time, so for QueryRow `WithResilience` **only performs the circuit breaker / pool checks** and does not hold a bulkhead slot.

## GORM

```go
import (
    bgorm "github.com/rushteam/beauty/contrib/gorm"
    "github.com/rushteam/beauty/contrib/sqldb"
)

db, _ := bgorm.Open(bgorm.Config{DSN: "...", MaxOpenConns: 50})
defer db.Close()

sqlDB, _ := db.SQLDB()

write, _ := db.ResilientWrite(sqldb.DefaultWriteResilience(sqlDB))
read,  _ := db.ResilientRead(sqldb.DefaultReadResilience(sqlDB))

write.WithContext(ctx).Save(&u)   // write + resilience
read.WithContext(ctx).First(&u, id) // read + resilience
```

You can also register the plugin manually:

```go
_ = db.Write().Use(bgorm.NewResiliencePlugin(sqldb.DefaultWriteResilience(sqlDB)))
```

## Bun

```go
import (
    bbun "github.com/rushteam/beauty/contrib/bun"
    "github.com/rushteam/beauty/contrib/sqldb"
    _ "github.com/go-sql-driver/mysql"
)

db, _ := bbun.Open(bbun.Config{
    Driver: "mysql", DSN: "...", Replicas: []string{"..."},
    MaxOpenConns: 50,
})
defer db.Close()

write := db.ResilientWrite(sqldb.DefaultWriteResilience(db.Primary()))
read  := db.ResilientRead(sqldb.DefaultReadResilience(db.Primary()))

write.NewInsert().Model(&u).Exec(ctx)
read.NewSelect().Model(&u).Where("id = ?", id).Scan(ctx)
```

When the circuit is open, the Bun hook fails fast via `context.WithCancelCause`, so the error may surface as `context.Canceled` (with cause `sqldb.ErrCircuitOpen`).

SQLite for tests:

```go
db, _ := bbun.OpenSQLite("file::memory:?cache=shared", bbun.Config{MaxOpenConns: 1})
```

## Configuration Reference

### PathResilience

| Field | Description |
|------|------|
| `Breaker` | Non-nil enables circuit breaking; nil disables it |
| `MaxConcurrent` | Bulkhead concurrency limit; 0 means unlimited |
| `MaxConcurrentWait` | How long to wait for the bulkhead; 0 rejects immediately when full |
| `Pool` | `*sql.DB`, used for pool saturation detection |
| `IsFailure` | Failure classifier; nil uses `DefaultIsFailure` |

### BreakerSettings Defaults

| Path | Threshold | MinRequests | Cooldown |
|------|-----------|-------------|----------|
| Write `DefaultWriteResilience` | 0.3 | 5 | 5s |
| Read `DefaultReadResilience` | 0.6 | 10 | 3s |

### Error Codes

| Error | Meaning |
|------|------|
| `sqldb.ErrCircuitOpen` | Circuit open, failing fast |
| `sqldb.ErrPoolSaturated` | Connection pool saturated |
| `sqldb.ErrConcurrencyLimited` | Bulkhead full |

The business layer can map these to 503 / 504 with `pkg/api/dberr`.

## Working Alongside Business Fixes

| Layer | Measures |
|------|------|
| Business | Make hot counters asynchronous, batch flushes, throttle single-row UPDATEs |
| Connection pool | Sensible `MaxOpenConns`; split read and write pools |
| Framework | This resilience layer — fail fast, limit amplification |

Reference incident: every page view synchronously ran `UPDATE template SET hot_score=...` → recovered once the synchronous write was removed from the application layer; in similar scenarios the resilience layer can prevent all 8 Pods from exhausting their pools at the same time.
